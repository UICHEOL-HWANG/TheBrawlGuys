## 1. 핵심 판단 — "리플레이급 로그"를 기반층으로

이 게임의 sim은 **결정적**이다 (같은 시드·경기장·설정·입력 → 같은 결과, 리플레이 해시 테스트로 매 커밋 검증).
따라서 **경기마다 모든 슬롯의 틱별 입력만 저장하면, 그 경기의 모든 상태(위치·속도·들고 있던 무기·대미지·판정)를 나중에 100% 재생성**할 수 있다.

| 층 | 저장소 | 역할 | 비고 |
|---|---|---|---|
| L0 리플레이 로그 | Supabase `match_inputs` | 모든 슬롯 입력 + 재현 메타데이터 | **모든 분석·모델의 원천**. 나중에 새 피처가 필요해도 재생해서 뽑는다 |
| L1 경기 요약·피처 | Supabase `matches`·`match_players` | 경기당 1행·슬롯당 1행의 정리된 피처 | SQL로 바로 분석, 모델 학습 테이블의 뼈대 |
| L2 희소 이벤트 | Supabase `match_events` | 타격·링아웃·아이템·기믹 등 | 재생 없이 빠른 SQL |
| L3 제품 행동 | Amplitude | 세션·퍼널·리텐션·실험 | 대시보드·코호트. 경기 내부는 요약만 |

**재현성 계약** — L0가 쓸모 있으려면 아래를 반드시 함께 저장한다. 하나라도 빠지면 재생 불가:
`seed`, `arena_id`, `player_count`, 슬롯별 `character`/`style`/`controller`, `config_fingerprint`(sim 그룹),
`sim_version`(`SNAPSHOT_VERSION`), `build_version`, **`final_state_hash`**(재생 결과가 원본과 같은지 검증용).
오프라인 재생기(헤드리스 Godot)가 `final_state_hash`를 대조해 **불일치 경기는 분석에서 제외**한다.

## 3. 추가로 기록할 것 (현재 대비 델타)

### 3.1 식별·버전·맥락 (모든 분석의 조인 키와 교란변수)
- 경기 헤더 추가: `config_fingerprint`, `sim_version`, `event_schema_version`, `final_state_hash`, `session_id`, `user_match_seq`(유저의 n번째 경기), `config_variant`(실험 변형 id, 기본 `control`)
- 슬롯 추가: `controller`(`local`/`bot`/`remote`), `bot_difficulty`, `bot_params_hash`
- 설치·유저 속성 (Amplitude user property): `first_seen_at`, `install_build`, `platform`, `input_device_primary`, 기기 모델·GPU·메모리 등급(성능 교란변수)
- 시간: 클라이언트 시각 + 서버 수신 시각(Supabase `created_at`) 둘 다 → 시계 오차 보정. 경기 내부 시간은 **틱**이 기준

### 3.2 경기당 행동 피처 (`match_players`에 컬럼 추가, 재생 없이 SQL로 쓰는 1차 피처)
- 입력: 액션별 누름 횟수(약·강·가드·잡기·점프·필살기), `inputs_per_min`, 방향 전환 횟수, 연타 비율(`combo_buffer_ticks` 안 연속 입력), 가드 유지 시간 비율
- 결과 효율: 공격 적중률(= hits / (hits + whiffs)), 가드 성공 수, 잡기 성공률, 최대 콤보 길이, 분당 대미지
- 방어·복귀 (스키마 8, tracking-plan §3.4.1): 구르기·공중 회피, 퍼펙트 가드, 가드 브레이크(당함·깸), 다운·낙법·기상 방식, 맞은 클린 히트 대비 DI 시도 수
- 실력·상황 (스키마 8): 위협 대비 반응 수·평균 반응 틱, 회피 성공, 낙법 시도 대비 성공, DI 각도(수직 비율)·텀블 생존, 가장자리·고% 상태의 가드·공격·회피 선택, 팀 어시스트
- 공간: 이동 거리, 가장 가까운 상대와의 평균 거리, 가장자리(반경 80% 밖) 체류 비율, 공중 체류 비율
- 아이템: 아이템별 보유 시간, 최초 획득까지 걸린 시간, 경합 획득(2m 안에 상대가 있을 때) 수
- 경기 흐름: 선취 링아웃 여부, 최대 스톡 열세에서 승리(역전) 여부, 마지막 스톡 진입 시각

### 3.3 세션·퍼널 (Amplitude)
- `session_started`/`session_ended`(길이, 경기 수, 마지막 화면) — 앱 종료·백그라운드 30분을 세션 경계로
- 로딩 시간: 부팅→로그인 화면, 로그인→타이틀, 경기 시작 로드 ms (체감 성능이 이탈의 큰 원인)
- 화면 체류: `screen_viewed`에 이전 화면·체류 ms, 선택 화면에서 **고민한 후보**(포커스한 카드 목록 → 인기 vs 실제 선택 차이)

### 3.4 좌절·몰입 신호 (M1·M7용, 나중에 복원 불가라 반드시 지금)
- 결과 화면 체류 ms, 재도전까지 ms, 결과 화면에서 메뉴로 나간 비율
- `match_abandoned`에 이탈 직전 맥락: 남은 스톡 차이, 마지막 링아웃 후 경과 ms, 일시정지 사용
- 연속 패배 수(세션 내), 패배 직후 설정 변경 여부
- 입력 공백: 경기 중 5초 이상 무입력 구간 수 (자리 비움 vs 포기 구분)

### 3.5 성능·오류 (교란변수 + 품질)
- 경기별 fps p5·p50, 프레임 스파이크 수, 틱 비용 p95, 품질 단계 → 이미 `perf_sampled`가 일부 담당. 경기 id로 조인되게
- 오류: 스크립트 오류·HTTP 실패·업로드 실패 수(요약), 크래시 직전 화면
- Phase 6 준비: `rtt_ms` p50/p95, 지터, 손실률, 재조정 크기, 끊김 사유 (넷코드가 체감에 미치는 영향 분리)

### 3.6 실험 준비
- 모든 경기·세션에 `config_variant` 기록. 원격 설정(Amplitude Experiment 또는 Supabase 테이블)으로 넉백·아이템 주기 등을 변형해도 **인과 분석**이 가능하게 노출(exposure) 이벤트를 남긴다

## 4. 저장 용량 설계 (Supabase 무료 500MB 기준)

현재 `match_events`에 0.5초 위치 샘플을 **행 단위**로 넣으면 4인 3분 경기에 약 1,400행 ≈ 200KB → **약 2,500경기면 무료 한도**. 선제 조치:

| 데이터 | 변경 | 경기당 예상 |
|---|---|---|
| 입력 로그 L0 | `match_inputs`: 슬롯당 1행, 변화 시점만 기록(런렝스) + gzip `bytea` | 수 KB |
| 위치 타임라인 | **보류 (2026-09-30 결정)** — 유저가 아직 적어 `match_events`의 0.5초 `pos` 행을 그대로 유지한다. 용량이 문제가 될 때 행 단위 샘플을 중단하고 경기당 1행 1Hz 압축 배열(`match_timeline`)로 바꾼다. 그 전에도 L0 재생으로 언제든 생성 가능 | (현행) 약 200KB |
| 희소 이벤트 L2 | 유지 (타격·링아웃·아이템·기믹) | 수십~수백 행 |
| 경기·슬롯 요약 L1 | 유지 + 컬럼 추가 | 1 + 인원수 행 |

→ 타임라인 압축을 적용하면 경기당 약 10~20KB로 **무료 한도에서 수만 경기**. 지금은 `pos` 행을 유지하므로 경기당 용량은 `pos` 행이 대부분을 차지한다(실측은 `dev/active/platform/platform-context.md` A7 항목). 한도가 가까워지면 ① `pos` 행 → `match_timeline` 전환, ② 오래된 L0를 Supabase Storage(파일)로 이관 순서로 줄인다.

## 5. 분석 파이프라인 (코드는 나중에, 결정 필요 항목 표시)

```
게임 ─▶ Amplitude (L3) ──(Export API)──┐
     └▶ Supabase (L0~L2) ──(Postgres)──┼─▶ analysis/ 워크스페이스 (Python)
                                       │     ├─ replay_features: 헤드리스 Godot로 L0 재생 → 타임라인·피처 파케이
                                       │     ├─ 모델: scikit-learn HistGradientBoosting (M1·M2·M5), 군집(M4)
                                       │     └─ 평가·기록: skore
```
- Python 스택은 `data-science-python-stack` 규칙을 따른다. **결정됨 (2026-10-01)**: pandas + pyarrow, matplotlib(정적 PNG), uv. 평가·기록은 skore 대신 우선 마크다운 리포트(`analysis/reports/`)로 한다.
- **구현 상태 (A9, 2026-10-01)** — [`analysis/README.md`](../analysis/README.md). 합성 데이터: `scripts/gen_dataset.gd`가 봇 경기를 게임 텔레메트리 코드 그대로 통과시켜 Supabase 테이블 모양 CSV + 1Hz `timeline.csv`를 만든다. 모델: M2 승률(GroupKFold), M5 밸런스(Wilson CI·로지스틱·링아웃 원인), M1 이탈(파이프라인만, 실사용자 필요). 실데이터의 타임라인은 아직 없음 — `match_inputs` 재생 추출기가 다음 단계.
- 재생 피처 추출기는 게임 코드(sim)를 그대로 쓰는 헤드리스 Godot 스크립트 → 학습 데이터와 게임 로직이 절대 어긋나지 않는다.

## 7. 구현 순서 (제안)
1. **A7** — L0 `match_inputs` + 재현 메타데이터 + `final_state_hash` + 오프라인 재생 검증 스크립트 (마이그레이션 0002). `match_timeline` 1Hz 압축은 용량이 필요해질 때까지 보류 (§4)
2. **A8** — §3.1 헤더·슬롯 컬럼, §3.2 행동 피처 컬럼, §3.3~3.5 세션·좌절·성능 이벤트 (EventCatalog·tracking-plan 갱신)
3. **A9** — `analysis/` 워크스페이스: 재생 피처 추출 + 첫 분석 노트(캐릭터·경기장 밸런스, 초기 이탈 퍼널). ✅ 1차 완료 (2026-10-01): 합성 600경기로 M2·M5 리포트, M1 파이프라인(스텁). 남은 것: `match_inputs` 재생 → 실데이터 타임라인, 실사용자 데이터로 M1·M5 재실행
4. **DDA / M3** — 난이도 다이얼·프로브·DDA (`PRD-BOT-03~06`, 스키마 9, 마이그레이션 0006). ✅ 1차 완료 (2026-10-01), 결과 `analysis/reports/dda.md`:
   - **M3 (1단계, 봇 기준 실력)**: 실력을 봇 다이얼 d 척도로 잰다. 합성 데이터에서 "플레이어" 슬롯 0은 d를 아는 봇 → 프로브 피처로 d를 회귀(실력 추정기, MAE·R²는 리포트). 사람은 첫 경기들에서 프로브 추정, 이후 기기별 레이팅(`user://skill.cfg`, EMA)으로 시작. 실사용자가 생기면 Elo/TrueSkill 류 상대 레이팅으로 확장 (봇 d를 상대 실력으로 사용)
   - **M2 + d (DDA용)**: 승률 모델을 d 피처(d_self·d_foe·d_diff)와 함께 로지스틱으로 재학습해 JSON으로 게임에 탑재(`res://data/models/win_prob.json`, GDScript 추론 = Python 예측, fixtures로 검증). DDA가 1 Hz로 사람의 상대 승률을 목표 대역(0.45–0.60)으로 유지하도록 봇 d를 조정
   - **실험**: `matches.dda_variant` on/off (기기 해시 버킷, 설정으로 강제 가능). 다음: 실사용자로 M1(재방문)·M7(좌절)을 라벨로 "몰입 최적 난이도" 학습 → 목표 대역 자체를 개인화(contextual bandit)
5. Phase 6 진입 시 §3.5 네트워크 지표
